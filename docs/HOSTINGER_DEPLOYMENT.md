# Deploy ITSSS CRM to Hostinger

Destination: **https://crm.itsss.co.in**.

Use **`outputs/hostinger-crm-upload.zip`** in Hostinger's **Node.js Web App**
deployment flow. This is a source ZIP with `package.json` at its root. Hostinger
installs the Linux dependencies and builds it on the server. The production
output is `.next/`, including the required `.next/standalone/server.js`.
The `postbuild` step copies `public/` and `.next/static/` into the standalone
server so images, JavaScript and CSS are served with it.

**This package needs Node.js hosting.** A PHP/static-only plan cannot run it by
extracting the ZIP into `public_html`. Hostinger documents Node.js Web App support
on Business and Cloud plans. Your exact plan has not been inspected. If hPanel
has no Node.js Web App option, this package requires a server-capable plan or a
separate Node.js server.

The older `itsss-production-build.zip` is the historical Cloudflare build and
must not be used for this deployment.

## Upload and build

### If deploying from GitHub

Hostinger builds the committed contents of the selected repository and branch.
Local edits and a newly generated ZIP do not update a GitHub-connected deployment.
The failed build for commit `720e823` still ran `node scripts/run-framework.mjs
build` (Vinext) and selected Node.js 22. That commit is the old version.

Publish the complete updated source to **`ITSSS-Ambala/itsss-erp`, branch `main`**
before redeploying from GitHub. Include the new runtime/auth files and scripts,
not just `package.json`; use the matching lockfile. The local Git remote may
still use the old `jabbersinghdhami/itsss-erp` URL, so confirm it targets the
repository connected in Hostinger. Keep private environment files, generated
outputs, `.next/` and `node_modules/` out of Git.

In **Settings & Redeploy**, select **Node.js 24**, **Next.js**, build command
`npm run build`, output `.next`, and apply the private environment values below.
An entry file is unnecessary for Hostinger's Next.js framework detection; if
manually requested, the generated server is `.next/standalone/server.js`.
Check that the new deployment uses a newer commit and logs `next build --webpack`
followed by `Hostinger server ready: .next/standalone/server.js`.

Do not point the output directory at `dist/standalone` to reuse the old build:
the old source still depends on Cloudflare bindings absent from Hostinger.

### If deploying from the source ZIP

1. Open **Websites > Create/Add Website > Node.js Web App / Web App**.
2. Select **Upload your website files** and choose `hostinger-crm-upload.zip`.
3. Use these settings:

   | Setting | Value |
   | --- | --- |
   | Framework | Next.js (backend/server application) |
   | Node.js version | 24.x |
   | Package manager | npm |
   | Root directory | ZIP root (`.`) |
   | Install command, if configurable | `npm ci --include=dev --include=optional` |
   | Build command | `npm run build` |
   | Output directory | `.next` |
   | Start command, if configurable | `npm start` |

   Next.js does not need a custom entry file. `npm start` validates private
   configuration and starts `.next/standalone/server.js` on Hostinger's assigned
   `PORT`, listening on `0.0.0.0`. Hostinger can also launch that generated server
   directly; API requests validate the same configuration. Use the standalone
   server for this build rather than `next start`.

4. Set the private environment variables below before deployment. Include
   development/optional dependencies during installation: TypeScript and
   Tailwind are needed to build.
5. Assign **crm.itsss.co.in** to this Node.js application using Hostinger's
   domain connection flow and complete the displayed DNS instructions.
6. Deploy. Confirm a successful build and a running server in Deployments/logs.
7. Confirm SSL is **Active** for `crm.itsss.co.in`, open `/login`, and sign in
   with the administrator email and the password used to generate its hash.

The local browser previously returned `ERR_SSL_PROTOCOL_ERROR` for this
subdomain. That check did not establish the exact cause; verify the domain
assignment, DNS and SSL status in hPanel.

## Private runtime settings

| Variable | Value |
| --- | --- |
| `ERP_PUBLIC_URL` | `https://crm.itsss.co.in` |
| `ERP_DATA_DIR` | An absolute, private, writable persistent directory, for example `/home/u123456789/itsss-crm-data` with your actual hosting username. |
| `ERP_ADMIN_EMAIL` | Your administrator email address. |
| `ERP_ADMIN_PASSWORD_HASH` | The complete value generated by `npm run auth:hash`. |
| `ERP_VAULT_KEY` | For a new workspace, the value generated by `npm run vault:key`. For migrated encrypted data, the original vault key. |
| `ERP_ADMIN_NAME` | Optional administrator display name. |
| `ERP_SESSION_HOURS` | Optional session duration, default `12`, maximum `168`. |
| `ERP_AUTH_USERS` | Optional JSON array for additional login accounts, default `[]`. |

Use Hostinger's Environment Variables screen. The ZIP contains `.env.example`
with placeholders; it contains no usable credentials or vault key. Do not put
private environment files into publicly served directories.

Create the private data directory outside `public_html`, `hbuilds`, and the
application directory. Hostinger overwrites deployment-managed folders when it
redeploys. An invalid/public data path is rejected by the app. The directory must
be writable by the Node.js application user; it contains both `workspace.sqlite`
and the private `files/` directory.

Generate the password hash locally with Node.js 24:

```sh
npm run auth:hash
```

The prompt hides the password and asks for confirmation. Use at least 12
characters. Copy the complete resulting `scrypt$...` string into the environment
setting without changing it. There is no default password and no public sign-up.

For a **new workspace only**, generate a 32-byte vault key:

```sh
npm run vault:key
```

Retain the key securely. Replacing it makes existing encrypted vault records
unreadable. Local `.dev.vars` secrets are deliberately excluded from the ZIP.

## Authentication and team access

Sign-in uses salted scrypt password hashes and random session tokens. Only token
hashes are stored in SQLite. Production cookies are Secure, HttpOnly,
SameSite=Lax and scoped to the subdomain. Sessions expire server-side; logout
revokes them; changing a configured password hash revokes existing sessions for
that account. Failed sign-in attempts are limited per configured account.

The configured administrator must make the first authenticated workspace request.
An additional account cannot claim an empty workspace. Initialization creates
that administrator as Super Admin and seeds the existing demo records.

To allow a team member:

1. Add an active user and role in the ERP's Users module. Map Technician/Client
   users to their employee/customer as before.
2. Generate that person's password hash using `npm run auth:hash` and add the
   matching email to `ERP_AUTH_USERS`, for example:

   ```json
   [{"email":"staff@example.com","name":"Staff Member","passwordHash":"PASTE_GENERATED_HASH"}]
   ```

3. Apply the runtime environment change. The account needs both a configured
   credential and an active ERP membership/role to access business data.

Password reset and two-factor authentication are not implemented in the UI.
Password changes are managed through private environment configuration. The old
ChatGPT identity headers and development mock cookies no longer grant access.

## Records, files and backups

SQLite replaces D1. Database schema initialization is automatic and workspace
writes still require the current revision, rejecting stale updates with HTTP 409.
Private disk storage replaces R2, preserving file metadata, authenticated
downloads, attachment checks and single byte-range media responses. AES-256-GCM
vault encryption remains in place.

This runtime is intended for one Node.js deployment with one persistent local
data directory. Do not run replicas on independent disks. Keep database and file
backups outside the deployment tree. Use a consistent SQLite backup operation
(or stop the app before copying the database), and back up `files/` and the vault
key as well. Copying an open WAL-mode database file alone is not a reliable backup.

The source ZIP and the fresh server do **not** include your old business data or
uploaded files. Manual JSON backup/restore can migrate records when the original
vault key is configured, but it contains file references rather than uploaded
bytes. Existing R2 objects and their metadata require a separate migration into
private storage. The initial workspace contains demo data; hiding its label
does not remove those records.

## Local verification

With Node.js 24:

```sh
npm run typecheck
npm test
npm run build
npm run verify:hostinger
npm run verify:hostinger -- --standalone
npm run package:hostinger
```

The production verification creates isolated synthetic credentials, records and
uploads, then checks login, rejection of forged identity headers, CSRF checks,
revision conflicts, encrypted backups, private downloads/ranges, restart
persistence and logout. Its temporary database/files are removed afterward.
It does not modify your existing Cloudflare/Wrangler local workspace. The
`--standalone` run copies only `.next/standalone/` to an isolated temporary
directory and verifies it without access to the source's installed dependencies.
Both modes check the actual JavaScript and CSS asset URLs as well as public files.

Verification artifacts are in `outputs/hostinger-smoke-verification.json` and
`outputs/hostinger-standalone-verification.json` and
`outputs/hostinger-package-verification.json`. A successful local build verifies
the Node.js app, not a live Hostinger deployment or DNS/SSL configuration.
